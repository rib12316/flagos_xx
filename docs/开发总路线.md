## 0. 开发模式

## 3. 单 agent 日常循环

```
每个开发日：
1. 环境自查：pgrep -f vllm 无残留 → ixsmi 显存空闲 → pip provenance 四重验证
2. 从 开发记录.md 取当前假设 → git checkout main && git pull → git checkout -b feat/<编号>
   （自最新 main 切出：验证与归因基于当前基线；diff main..feat 只含本假设改动）
3. 开发 → T0 micro-bench（秒级，不过线当场 revert）
4. T1 官方脚本单场景（10-20min）→ 过线才 commit
5. 动了数值逻辑 / 阶段收官 → T2 双场景 + evalscope 全量
6. 台账回写 → 验证全过线：git checkout main && git merge feat/<编号> && git push
   （合入即成为下一假设的新对照基线）；下一假设从新 main 切出
一次只改一个变量；bench 等待间隙写下一任务的代码/脚本。
```

## 4. 纪律（违反任何一条 = 数据作废或成绩无效）

1. **RSI 台账制**：改动前登记（目标文件/函数+机制+预期指标），改后回写实测；不可解释的收益不可复现、写不了报告。
2. **pip provenance 四重验证**（F5 教训）：来源指向本仓库 / diff 一致 / 旧仓库 patch 符号不存在 / flag_gems==v5.3.5。**旧仓库 `/flagos_比赛/flagos2_infragogogo` 的使用边界（参考开发）**：允许**只读参考**——其 patch 实现（如 launch 调优）、bench 脚本模板、历史实测数据均可作为移植蓝图与证据引用（注明口径）；**禁止** pip install 自该路径、禁止直接 merge/cherry-pick 其分支——一切改动在 `baseline-2026-11-03` 上重实现，`git diff baseline` 只显示本队自己的改动。
3. **GPU 独占**：任何 serve/bench 期间不并发其他 GPU 任务（±1% 判定带要求）。
4. **改动落点**：只改 `vllm-plugin-FL/`、`FlagGems/`；serve 参数、bench 脚本、评测口径一个字不动。
5. **当日 push**：实例会被回收；所有产物（方案/日志/CSV）回写本仓库 `docs/`、`results/`。

## 5. 当前任务：D0 · attention launch 调优复证与固化

**假设**：废弃版 monkeypatch 证据（decode w1/s1、prefill w2/s1 → 4K +41.7% / 16K +46.6%，对照 +1.35%）在纯净基线上机理成立；固化为 dispatch 层 per-shape launch config 后双场景 +20% 量级。

**步骤**：
1. **情报回收（旧仓库只读参考）**：在 `/flagos_比赛/flagos2_infragogogo` 中定位 launch 调优的原始实现——grep `patch_unified_attention_launch_for_iluvatar`、翻 git log/全部分支找 D3a/D3c 提交；读懂 patch 落点（哪个函数、哪个调用点、decode w1/s1 与 prefill w2/s1 如何注入）；顺带回收 `results_local/prof/micro_bench_attn.py` 模板与历史实测数据（引用注明口径）
2. 分支 `feat/d0-launch-tune`（自 `baseline-2026-11-03`）+ 从本仓库安装 + provenance 四重验证
3. **复证（T0，无源码改动）**：进程内 monkeypatch 对照 bench——bs=64、kv_len∈{4096,16384}、2KV×head_dim128；default vs decode w1/s1 / prefill w2/s1；判据：有效带宽差 ≥10%
4. **固化（复证通过才做）**：launch config 以**数据驱动的 per-shape 配置表**形态落在 dispatch 层（iluvatar 路径），默认启用；配置按（decode/prefill 路径 × bs 档 × kv 长度档）索引，由 `scripts/` 下 sweep 脚本生成——**不硬编码单值**（防后续阶段使最优点漂移，重调=重跑脚本换表）
5. **验证**：T0 确认新配置生效 → T1 官方脚本 4K+16K（对照 1879.68/862.06）→ 阶段末 evalscope 一次（launch 不改数值，抽查即可）
6. **收尾**：台账回写（预测 vs 实测）+ push；T1 不过线 → revert 记录，转小 M GEMM 调优

**重调检查点（防组合后次优）**：D0 交付的是「调优机制+首版参数」，非最终参数。① P2′ 调度落地后（批分布变）；② P3′ 量化落地后（显存预算变）；③ **冻结前终扫**（11/16-17，最终组合形态下重扫配置表 + 沐曦 per-vendor 独立扫）。每次 ~1h GPU。台账中 D0 状态标注「需组合后重调」直至终扫完成。

**时间盒**：1 天。**风险**：纯净版不复现（triton 3.2 默认值差异）→ 如实记录转 GEMM 项。

## 7. 关键事实速查（实测已证）

- 天数 BI-V150：容器可见 32GB；KV 池 ≈21GB（521,936 tokens）；16K@64 并发需 46.3GB → **容量排队型**（同驻上限 29，ISL 准入 31-32），抢占待 T2 metrics 裁决
- 沐曦 C500 64GB：KV 预算 45-48GB vs 需求 46.3GB → **临界区**，H1 准入预留主战场
- decode 流量：16K 91% / 4K 71% 在 KV 读取（attention kernel）；GEMM 占 4K ~29%；元素融合上限 ~2%
- W8A8 管线已在本仓库 `vllm-plugin-FL/vllm_fl/quantization/w8a8/`（缺转换脚本）；BI-V150 上报 sm(7,1)：cutlass int8 快路径必不触发，通用 Triton `scaled_mm` 是否走 MMA 待闸门实测；两卡均无 FP8
- KV int8：容量 1.94× 机制成立，但独立路径已证伪（精度崩/prefill -25%/无硬件加速）——唯一翻案 = 与 attention 重写合并
- 显存耦合精确数：W8A8 落地释放 ≈1.84GiB（embed/lm_head 保 bf16 不量化）→ KV +8.8%（同驻 +3-4 条）

贯穿全程：改动纪律（RSI 循环 + 三条新规）

每个优化改动走同一条流水线：假设台账登记（目标文件/函数 + 预测机制 + 预期指标）→ 起草 patch → T0/T1 验证 → 过线才 git commit，不过线 revert 并记录失败原因。一次只改一个变量。台账到 P4′ 直接变成 report.pdf 的 ablation 表。实测阶段用代价换来的三条新规：

  1. pip provenance 纪律：任何测量前验证插件来源（diff/md5/patch 符号消失/flag_gems 不变 四重验证）——F5 教训：装错版本一天白跑。
  2. GPU 自查纪律：单 agent 串行开发模式（2026-11-03 起，替代三线并行）：每个 GPU 步骤前自查进程与显存（pgrep -f vllm + ixsmi）；若实例仍有其他会话在跑，维持公告板协调；kill 前三重确认（无活动 bench / CSV 停更 / 仅剩孤儿）。
  3. 废弃仓库数据口径：旧仓库的 D3a/D3c、KV 量化负结果、profile 数据只作证据引用并注明口径，不作代码基线（队伍已定重头开始：唯一开发仓库 = github.com/rib12316/flagos_xx，基线 tag baseline-2026-11-03 = 上游 flagos-2026-s2 @13eb9be + FlagGems v5.3.5；旧仓库 flagos2_infragogogo 完全隔离）。

P1′ · launch 调优固化 + 算子清扫 11/04 – 11/07 ｜ GPU ≈5h

主菜 D0：把 attention launch 调优固化为源码。证据：废弃版 monkeypatch（decode w1/s1、prefill w2/s1）曾拿 4K +41.7% / 16K +46.6%，对照组禁用 patch 仅 +1.35%。A 线 T4 将以进程内 monkeypatch 复证机理，复证通过后落成 dispatch 层 per-shape launch config 或 FlagGems tune config（源码形态，默认启用）。合法性：kernel 执行配置调优属于框架内算子优化（FlagGems tuning 机制的本来用途），非 serve 超参、非 bench 调优。跨平台：unified_attention 是跨平台 Triton kernel，沐曦侧预期同收益但需重调参数（见沐曦窗口）。

P2′ · 调度分治 11/06 – 11/12 ｜ 天数为主，沐曦机会窗口穿插 ｜ GPU 天数 ≈4h + 沐曦 ≈4h

前提已具备：C 线 T6 已验证插件内注入 SchedulerFL 可行（platform.py env 门控钩子）；T2/T3 出抢占裁决。按卡分治：

天数侧（容量排队型，预判弱抢占 → 分支 B）：① H3' 波次准入节奏/提前插入——旧日志指纹「16K 每 ~20s 才准入 1 条、prefill 混入步把 decode 打到 11-17 tok/s」，混批结构是主杠杆；② H4 block_size 16→64（块表 32,621 块管理开销降 4 倍，flagtree 页粒度需实测）；③ H6 prefix caching 旁路（随机 token 零命中，1024 块哈希/条纯 CPU 浪费）；④ H1 准入预留降级为保险项（T3 已实测其净值）。

沐曦侧（真·临界区 45-48GB vs 46.3GB，H1 主战场）：机会窗口（抢到节点即开跑，工作包预置：基线复跑 → D0 参数重调 → 16K 抢占证据采集 → H1 准入预留 A/B）。

P3′ · W8A8 动态量化 三重闸门 ｜ 11/13 – 11/17 ｜ GPU ≈4h

主案（已决策采纳 B 线）：W8A8 动态 int8（per-channel 权重 + per-token 动态激活，无校准），checkpoint config 驱动（绕开「禁超参开量化」红线）。管线已完整存在于 vllm_fl/quantization/w8a8/，唯一开发件 = bf16→int8 转换脚本（B 线 T5 已产出种子函数）。退路链：仅 MLP 混合 → W8A16 weight-only。显存收益（B 线 T3 精确测算）：释放 ≈1.84GiB → KV +8.8% ≈ 568K tokens（同驻 +3-4 条，与调度正向叠加，但不消除排队）。

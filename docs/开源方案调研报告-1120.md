## 逐项详注

### F3 KV cache 量化（int8/FP8）——外部证据最强的"真杠杆"，但门在我们栈上是闭的
- 外部：vLLM 官方博客（H100+FA3，Llama-3.1-8B）decode ITL 斜率压到 bf16 的 54%，真实负载输出吞吐 **+14.9%**，精度最多掉 1-2 分（3-0 票确认）。
- 我们的一手证据改写其两段收益来源：
  - 「KV 内存省 2×→调度塞更多并发」：**C500 容量收益=0**（池 1.26M tokens、零 preempt、Running 63-64/Waiting 0-1——今日实测）；
  - 「KV 读取字节减半→attention 带宽减半」：要求 attention kernel 内 dequant——**MACA flash 闭源 bf16-only**（B 机 D6 判决：自研替代 kernel 0.25-0.54× 落败，flash 已 83-88% 带宽利用）。
- **行动（唯一能开这扇门的钥匙）**：向沐曦（vendor）要 int8-KV flash attention 支持，或确认 mctlass/flash 后续版本路线。若 vendor 提供，D8 立即复活且预期 16K decode +10-20%。
- 精度预算警告：W8A8 之上叠 KV int8，math_500 门 0.95 仅 3pp 余量，必须实测。

### F6 CUDA Graph 全图模式——配置已是默认，实效被后端静默降级
- 外部（3-0）：FULL_AND_PIECEWISE 为 v1 默认、小模型通常最优；但全图捕获依赖 attention 后端声明（AttentionCGSupport 枚举，未声明=NEVER→自动降级）。
- 我们实测：serve 配置 dump 显示 cudagraph_mode=FULL_AND_PIECEWISE，但捕获进度条只有 "PIECEWISE"——**正是文档警告的静默降级**；且 d4 时 FULL_DECODE_ONLY 形态比无 config 慢 9.9%（4K）。
- 行动：一行 grep 查 MACA 后端的 CG 支持声明即可关账；若未声明，此项封死（plugin 无法绕过后端能力）。

### F7 torch.compile 定制融合 pass——机制可注入，收益取决于我们自己的融合目标
- 外部（3-0）：自定义 pass 经 PostGradPassManager/插件进程内改默认值注入，无需改 vLLM 源码；官方 ActivationFusionPass（SiLU+quant 融合）+8% 上限=可融合项占比（MI300 上取得，非 NVIDIA 先例）。
- 我们的落点：norm(0.6ms)+quant(1.55ms)/步，RMSNorm→per-token-quant 融合（norm 输出直接产 int8+scale）理论省 ~0.7-1ms/步 ≈ **2-3%**；为 MACA triton 写，走 T0→T1 纪律。
- 风险：metax inductor/triton 成熟度（本日已知：复杂 kernel 有 ATU 崩溃前科，简单 elementwise/reduction 类安全）。

### F1/F2 投机解码家族——外部证据完全支持今天的死刑判决
- EAGLE-3 论文自测（A100/vLLM/8B）：bs2 1.75× → **bs56 1.01×**（EAGLE-1 bs≥24 转负）；vLLM 官方定位"中低 QPS memory-bound"。我们 bs=64 + busy 96% + W8A8 近算力上限 → 前提不成立（3-0 票）。
- ngram/suffix：唯一"不增加峰值负载"的成员，官方称收益 modest，社区有大 batch 转负先例（issue #16258）；无损性保证限于硬件精度内，开后仍须重跑 math_500。低优先。
- 附：draft 模型训练成本（68K+464K 样本，8× EAGLE-1）+ W8A8 分布拟合——工程上也不成立。

### F5 overlap/异步调度——好机制，但天花板被我们自己的 busy 96% 压死
- 外部（3-0×3）：V1 架构重构 1.7×（kernel 几乎相同、纯 CPU 开销削减）、SGLang overlap 1.1×/1.3× 且小模型最显著、异步调度 v0.14 起默认开。
- 我们：busy 96% → 上限 = 4% 间隙回收；0.24 大概率已默认开。行动=核对 `SchedulerConfig.async_scheduling` 实际值（若因插件链路被关，开回是免费小钱）。

### F4 APC——已在最优态
- 官方（3-0）：只加速 prefill 不加速 decode；V1 近零开销默认开。我们实测 ON、官方 bench APC=0%（随机 token 无共享前缀）。无事可做。

### F8 DualPace——仅思想
- GPU+CPU 双引擎 decode（AMX 使能），独立运行时与冻结约束冲突；KV 容量充裕场景不对齐。可记的思想：GPU 饱和后主机算力承接溢出请求。

## 综合结论

外部全景与今日双机实测**独立收敛到同一结论**：在 64 并发、GPU busy 96%、attention 带宽 83-88%、量化近算力上限的部署上，
开源世界的常规手段（投机解码/overlap/图模式/缓存）收益全部落在 0-4% 区间；**唯一 >10% 级的候选（KV 量化）被闭源 vendor kernel
门控**——钥匙在沐曦手里（int8-KV flash 支持）。自主可控的剩余项只有 norm+quant 融合（~2-3%）与异步调度核对（0-4%）。

### 建议行动清单（按性价比）
1. 【问 vendor】向沐曦询 int8-KV flash attention 支持/路线（解锁 D8，16K decode +10-20% 预期）
2. 【5 分钟】核对 async_scheduling 与 MACA CG 支持声明两个默认值（关账或捡小钱）
3. 【半天】norm+quant 融合 pass（T0/T1 纪律，+2-3%）
4. 【存档】本报告 + 台账 §9 构成完整审计链

## 1. 网络与克隆

github.com HTTP 被墙；**SSH 直连（git@github.com:22）实测可用且即时无缓存**，ghfast.top 镜像有分钟级缓存滞后。策略：**优先全 SSH，ghfast 只做备用**：

```bash
git clone git@github.com:rib12316/flagos_xx.git        # SSH key 已加 rib12316 账号时首选
# 若 SSH 不通，退路：git clone https://ghfast.top/https://github.com/rib12316/flagos_xx.git
#   然后 git remote set-url --push origin git@github.com:rib12316/flagos_xx.git（push 必须走 SSH）
cd flagos_xx
git remote add ghfast https://ghfast.top/https://github.com/rib12316/flagos_xx.git 2>/dev/null || true
git fetch origin && git checkout delivery/s2-final  # 二期统此分支开发（提交锚点=tag delivery-final-1119）
```

**两个已踩过的坑（A 机实测）**：
1. **单分支 fetch 遗留**：clone 若带 `-b <branch> --single-branch`（或被配过），`git fetch` 只更新那一个分支 → 同步协议瞎掉。修复：`git remote set-branches origin '*'`（ghfast 同理）。**bootstrap 完成后必查**：`git config --get-all remote.origin.fetch` 应为 `+refs/heads/*:refs/remotes/origin/*`。
2. **ghfast 缓存滞后**：镜像上的分支 tip 可能比真实远端旧几分钟——用它判断"远端无更新"会误判。凡走镜像 fetch 的机器，重要比对前 `git ls-remote git@github.com:rib12316/flagos_xx.git` 复核。

- 若 SSH key 未配：`ssh-keygen -t ed25519` 后把公钥加到 rib12316 账号（请用户操作），否则只能 fetch 不能 push。
- ghfast 单点故障：本地继续干，恢复后 push。

## 5. 自动同步协议（双机在线协作的生命线）

**每 20-30 分钟检查一次 GitHub 远端**，双机对称执行：

1. **Claude Code agent（推荐）**：用定时任务（CronCreate），例如 `13,38 * * * *`，prompt 固定为：
   > 运行 `bash scripts/d5/sync_collab.sh` 检查远端更新。若有：(a) 任务板有 B/A 机新留言或状态变化 → 读并按需响应；(b) origin/delivery/s2-final 领先且本机无未提交工作 → `git merge --ff-only origin/delivery/s2-final`；(c) 出现新的 feat/ 分支 → 了解内容，若是给自己的交接（看提交信息）就接手；(d) 自己有未 push 的提交 → push。若 15 分钟内无法处理，在任务板自己区块标 blocked+原因。
2. **无 agent 时的兜底**（纯终端保活，只记录不响应）：
   `nohup bash -c 'while true; do bash scripts/d5/sync_collab.sh >> /tmp/sync.log 2>&1; sleep 1500; done' >/dev/null 2>&1 &`
3. 心跳：每次 sync 若发现远端更新，处理完在任务板「留言区」追加一行时间+摘要（这是对方判断你在线的唯一信号）。
4. 离开/休眠前：任务板自己区块标 `away`+时刻。

**同步检查是幂等只读的**（fetch + 比对 + 打印建议），不会自动 merge feat 分支、不会破坏工作区——放心高频跑。

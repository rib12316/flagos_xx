## 0. 三线研究的三个改写认知的结论

1. **逐元素融合不是主战场**（Track A）：按 decode 步时流量预算，16K 场景 91%、4K 场景 71% 的流量在 KV cache 读取（attention kernel），GEMM 权重仅占 4K 的 ~29%。RMSNorm/RoPE/SiLU-mul 融合单项收益封顶 ~2%。主杠杆是 **decode attention kernel** 与 **小 M GEMM 调优**。
2. **W8A8 管线在插件里已经存在**（Track B）：`vllm_fl/quantization/w8a8/` 有完整 packed scheme + FL 线性 kernel + FlagGems scaled_mm，稠密 Linear 直接适用，checkpoint config 驱动（无需 serve 超参）。唯一缺口是 bf16→int8 转换脚本（4-8h）。双卡 int8 均硬支持（C500 480 TOPS / BI-V150 384 TOPS，均 2:1 于 FP16；两卡均无可用 FP8）。
3. **16K 场景大概率在抢占重算，且重算 token 不计分**（Track C）：官方 bench 是随机 token（prefix caching 零命中）、每条恰好输出 1024、Total tok/s=(输入+输出)/时长。抢占→num_computed_tokens 清零→全量重算 = 纯浪费。插件内已有替换 scheduler_cls 的先例（worker.py:206-211），调度层是空白赛道 + 创新分主战场。

## 3. P2 量化批次（第 12 天决策闸门，Track B）

| 项 | 结论 |
|---|---|
| 推荐主方案 | **W8A8 动态 int8**（per-channel 权重 + per-token 动态激活，无校准）：decode 权重流量 4.5GB→2.3-2.8GB（受限段 1.6-1.9x），另省 ~2GB 显存缓解 16K KV 临界 |
| 现成资产 | vllm_fl/quantization/w8a8/ 整条管线已在插件内；FlagGems 有 metax/iluvatar 各自 int8 Triton matmul；唯一缺口 = bf16→int8 转换脚本（4-8h），总工作量 12-24h |
| 退路 | ①仅 MLP 混合量化（lm_head/embed 保 bf16）→ ②W8A16 weight-only（FlagGems weight_int8pack_mm 现成，近无损，+8-16h） |
| 排除 | FP8（两卡均不可用）、int4/GPTQ/AWQ（2B 模型+无校准工程量）、KV int8（与 A-H1 冲突，二期） |
| 硬约束 | 余量仅 1.2pt；math_500 全量一票否决；不过线立即退级；合入后 16K 临界区分析重算（KV 预算变化会吃掉 C-H1 部分价值） |

## 4. 交叉耦合与顺序纪律

- **B 合入 ⇒ 重算 16K 临界区**：权重省 ~2GB → 抢占压力下降 → C-H1 剩余价值需重测。顺序：C-H1 先落地拿分，B 后合入并重基线。
- **A-H1 与 B 的 KV int8 互斥**：都动 attention kernel，KV int8 明确排到二期。
- **验证串行**：单 GPU 独占跑分（±1% 判定带）；micro-bench（秒级，stdout）→ 单场景 bench（分钟级）→ 全量精度回归（仅数值改动与提交前）。
- **天数卡到位即成第二验证队列**：优先重放 A-H3 修复 + 跨平台项（A-H2/C-H4），vendor 专属项（A-H1）不可跨。
